# NeoLoader — архитектура и функционал

Документ для ИИ/разработчика, впервые открывающего этот репозиторий. Описывает
устройство системы целиком: процессы, потоки, протокол между слоями, ключевые
инварианты и то, почему они реализованы именно так (а не "как правильно по учебнику").

## Что это

Десктопное Windows-приложение для скачивания видео/аудио с YouTube через yt-dlp,
с опцией скачивания русской дублированной аудиодорожки ("нейродубляж" — фактически
это официальная авто-дублированная дорожка YouTube, а не отдельный AI-пайплайн
внутри приложения). Раньше был чисто PyQt-виджетный UI (`ui/main_window.py`,
доступен через `--legacy`), сейчас основной UI — React-приложение (NeoLoader),
хостящееся внутри `QWebEngineView`. С этой сессии — упаковывается в один EXE
(PyInstaller onefile) и живёт в системном трее.

## Процессная модель

Один процесс, три уровня параллелизма внутри него:

```
main.py (main/GUI поток, Qt event loop)
 ├── QApplication + WebMainWindow (QWebEngineView, грузит frontend/dist/index.html)
 ├── TrayIcon (QSystemTrayIcon) — живёт всё время работы приложения
 ├── SingleInstanceServer (QLocalServer) — слушает повторные запуски EXE
 │
 ├── [фоновый Python-поток] uvicorn.Server — FastAPI, HTTP+WebSocket на 127.0.0.1:8756
 │    └── DownloadManager (QThread) — цикл "запусти доступные задачи из очереди"
 │         └── [обычные threading.Thread, по одному на активную загрузку] _run_item()
 │              └── yt-dlp (синхронный, блокирующий) + ffmpeg-постпроцессинг
 │
 └── React-фронтенд внутри QWebEngineView — отдельный Chromium-процесс/поток,
      общается с бэкендом только по HTTP (fetch) и WebSocket (ws://127.0.0.1:8756/ws)
```

Frontend и Python-бэкенд полностью развязаны по процессам: React ничего не знает
про PyQt, PyQt ничего не знает про React — весь контракт между ними это
HTTP JSON API + один WebSocket-канал событий (`api/server.py`). Это значит
фронтенд можно точно так же гонять и через `npm run dev` (Vite, порт 5173) на
живом бэкенде — так и ведётся вся фронтенд-разработка/тестирование.

## Бэкенд

### `core/settings_manager.py` — `SettingsManager`

Простое key-value хранилище в JSON. Путь к конфигу зависит от режима запуска:
- из исходников (`python main.py`) — `<репозиторий>/config/settings.json`;
- из собранного EXE (`sys.frozen == True`) — `%APPDATA%\NeoLoader\settings.json`.

Это принципиально: PyInstaller onefile распаковывает всё в temp-папку заново при
каждом запуске, поэтому писать настройки/историю "рядом с exe" нельзя — они
исчезнут при следующем старте. `_resolve_config_dir()` в начале файла — единственное
место, которое это решает.

Также хранит историю завершённых загрузок (`history`, максимум 50 записей,
последняя — первая).

### `core/video_info.py` — анализ ссылки без скачивания

`VideoInfo.fetch(url, noplaylist=True, settings=None)` — один `extract_info(download=False)`.
`settings` появился позже и обязателен по смыслу: раньше анализ ходил в YouTube БЕЗ
прокси и БЕЗ кук из браузера, хотя скачивание их использовало, — анализ и загрузка
видели разные наборы форматов. Общие опции вынесены в `base_ydl_opts(settings)`.
`noplaylist=True` по умолчанию критичен: если открыть видео из YouTube-микса/радио,
в URL подставляется `list=RD...`, и без этого флага yt-dlp пытается извлечь ВЕСЬ
(бесконечный) плейлист вместо одного видео — раньше это выглядело как вечный
"Analyzing..." в UI. `detect_link_type()` в этом же файле решает, когда `noplaylist`
можно/нужно ставить в `False` (сама ссылка — плейлист).

`has_ru_dub` в ответе — `any(normalize_lang(f["language"]) == "ru" for f in formats)`.
Строгое `== "ru"` (как было раньше) — БАГ: YouTube отдаёт `ru-RU` у русского
оригинала и `en-US` у английского, поэтому у русскоязычных роликов дорожка
«не находилась». Сравнение идёт по базовому коду (`normalize_lang` в `resolver.py`).
Дальше по тексту:
YouTube сам маркирует дорожки метаданными `language`/`format_note` для тех видео,
где ролик официально продублирован (auto-dub). Если этого поля нет — значит у
конкретного видео на стороне YouTube нет русской дорожки вообще, приложение тут
бессильно (это подтверждено многократно во время тестирования: часть "примеров
для скачивания с нейродубляжом" от пользователя на деле не имела RU-дорожки —
не баг приложения, ограничение конкретного видео на YouTube).

### `core/resolver.py` — snapshot-based резолвинг форматов

Ключевая архитектурная идея всего пайплайна скачивания, стоит понять её первой:

YouTube отдаёт **нестабильные** списки форматов между отдельными запросами
(антибот-защита режет ответ по-разному раз от раза). Если резолвить "какой
format_id качать" заново на каждой fallback-попытке — можно поочерёдно попасть
в границы разных ответов и никогда не совпасть, хотя реальный набор потоков
не менялся.

Решение: `extract_info()` вызывается максимум 1–2 раза за скачивание
(`build_snapshot_with_retry` — второй раз только если нужна `ru`-дорожка, а её
не видно в первом снапшоте), результат замораживается в неизменяемый
`VideoSnapshot`, и весь дальнейший резолвинг (`build_download_plans`) работает
**только** с этим одним снапшотом, без единого нового похода в сеть.
`build_download_plans` строит упорядоченный список `DownloadPlan` — от точного
запроса пользователя (нужное качество + кодек + `ru`-аудио) до maximally
permissive fallback (progressive/muxed поток). Каждый план содержит уже
**конкретные `format_id`**, а не строку-селектор — `validate_plan()` проверяет,
что эти ID реально есть в снапшоте, до похода в yt-dlp. Это устраняет целый
класс ошибок "Requested format is not available", которые бывают у наивной
реализации (выбрал формат на одном ответе YouTube, скачивать пошёл — а yt-dlp
внутри себя переизвлёк список и этого ID уже нет).

`DownloadManager._run_pipeline()` идёт по списку планов по порядку, на каждом
создаёт **новый** `YoutubeDL` с `format` в опциях конструктора и делает один
настоящий `extract_info(url, download=True)` (переиспользование одного `ydl` +
`process_video_result()` на уже обработанном `info_dict` ненадёжно для языковых
`format_id` вида `140-14` — см. развёрнутый комментарий в коде).

**Инвариант порядка планов (ru-first).** Если пользователь попросил русскую
дорожку и она есть в снапшоте, то ВСЕ планы с ней стоят строго раньше любого
плана без неё. Это чинит главный симптом «скачал с дубляжом — дубляжа нет»:

* раньше брался ровно один «лучший видео-поток ≤ запрошенной высоты» под фильтр
  кодека; если под фильтр не подходило ничего, весь блок «видео + ru-аудио»
  пропускался целиком, и следующим планом шёл **progressive (muxed)** поток —
  у него единственная и ВСЕГДА оригинальная звуковая дорожка. Загрузка
  завершалась успешно, галка стояла, звук был оригинальный;
* теперь по видео строится **лестница** (`_video_ladder`) — от запрошенной
  высоты вниз по всем доступным, сначала с фильтром кодека, потом без него,
  и ru-дорожка отваливается только если её реально нет в снапшоте.

Дополнительно `_best_audio(..., prefer_dubbed=True)` при нескольких `ru`-дорожках
(оригинал + авто-дубляж) выбирает именно дублированную (`is_original_track()`
читает `format_note` вида `"... original (default)"`).

### `core/download_manager.py` — `DownloadManager` (QThread) + `QueueItem`

Очередь: `add_to_queue()`/`remove_from_queue()`/`get_queue_snapshot()`, защищены
`threading.Lock`. `run()` — цикл на `threading.Event` (`self._wake`) с таймаутом 1с:
просыпается сразу при `add_to_queue()` и при освобождении слота, в простое не
тратит CPU (раньше был безусловный `time.sleep(0.3)`, то есть 3 пробуждения в
секунду вечно, даже когда приложение просто висит в трее). Зовёт
`_launch_available()`, которая смотрит `concurrent_downloads` из настроек и
запускает столько `STATUS_PENDING`-задач параллельно (каждая — отдельный
`threading.Thread`), сколько свободно слотов. При `concurrent_downloads=1`
(дефолт) поведение эквивалентно строго последовательной очереди.

У каждого `QueueItem` — свой `pause_event: threading.Event` и `cancelled: bool`
(раньше это было одно общее поле на весь менеджер — ломалось, как только
скачивались две задачи параллельно). Пауза/отмена проверяются **только** внутри
`progress_hook` yt-dlp — это единственная безопасная точка прервать скачивание
(`QThread.terminate()` может повредить файл на диске).

Пайплайн статусов одной задачи:
```
queued → analyzing → resolving → starting → downloading → [merging|converting] → completed
                                                          ↘ paused (обратимо)
любой шаг → failed / cancelled
```

**Троттлинг прогресса** (`_make_progress_hook`, добавлено в этой сессии): yt-dlp
дёргает `progress_hooks` на каждый прочитанный чанк — на быстром соединении это
могло быть сотни раз в секунду. Каждый вызов раньше безусловно эмитил Qt-сигнал
→ WebSocket-событие → React `setState` → перерисовку прогресс-бара (framer-motion)
в `QWebEngineView`. При достаточной частоте это забивало главный поток рендерера
Chromium настолько, что клики (например, по "Настройки" в сайдбаре) переставали
обрабатываться вовремя — воспринималось как "настройки иногда не открываются",
а если так копилось достаточно долго — Windows мог посчитать окно зависшим.
Сейчас эмит ограничен: не чаще раза в 250мс, кроме случаев, когда процент скакнул
минимум на 1% (чтобы прогресс не выглядел дискретным на очень быстрых закачках).

**Тег русской дорожки** (`_tag_ru_audio`, добавлено в этой сессии): yt-dlp
корректно выбирает и скачивает DASH-поток с `language=ru` (это метаданные
YouTube, не догадка приложения) — но при склейке видео+аудио через ffmpeg merge
не проставляет `language` в итоговый контейнер, и `ffprobe` после обычного
`download()` показывает `eng` даже для честно русской дорожки (проверено
напрямую: голый yt-dlp без единой строчки кода этого приложения показывает тот
же результат — баг/недоработка на стороне yt-dlp, не этого проекта). Поэтому
после скачивания, если `item.neuro_dub_ru`, делается один stream-copy remux
(`ffmpeg -c copy -metadata:s:a:0 language=rus`, без перекодирования) — только
после него файл проверяется `_probe_audio_language()`.

### `api/server.py` — мост FastAPI/WebSocket ↔ Qt-сигналы

`create_app(settings, download_manager)` создаёт FastAPI-приложение. Все
HTTP-эндпоинты — обычные синхронные `def` (не `async def`), поэтому FastAPI/Starlette
сам гоняет их в threadpool — блокирующие вызовы (`settings.save()` = запись
JSON на диск, `shutil.which`, `subprocess` для `ffmpeg -version`/`pip install`)
не подвешивают event loop и не мешают WebSocket-трансляции. Проверено под
нагрузкой (см. "Проверено в этой сессии" ниже) — `/api/settings`,
`/api/diagnostics` отвечают за 50–90мс даже во время активной загрузки.

Сигналы `DownloadManager` (`progress_changed`, `status_changed`, `log_message`,
`error_occurred`, `item_finished`) подключены к `emit_event()` через
**`Qt.ConnectionType.DirectConnection`** — это обязательно, а не опционально:
приёмники — обычные лямбды без своего `QObject`, а `DownloadManager` эмитит
из фоновых `threading.Thread` (не только из своего `QThread`). Без явного типа
подключения PyQt может выбрать `QueuedConnection` к прокси-объекту в главном
потоке — и тихо терять доставку, если тот не успевает её выкачивать (это был
реальный баг в предыдущей сессии: `item_finished` не доходил, история не
обновлялась).

`emit_event()` сама по себе — потокобезопасный мост: `loop.call_soon_threadsafe()`
кладёт событие в `asyncio.Queue`, единственный `_broadcast_worker()` таск
вычитывает очередь и рассылает `ws.send_json()` всем подключённым клиентам
(`app.state.clients`). Так события из Python-потоков безопасно попадают в
asyncio event loop без прямых вызовов asyncio API из чужого потока.

Эндпоинты: `/api/analyze` (запуск `VideoInfo.fetch`), `/api/queue` (CRUD +
`/pause`, `/resume`, `/cancel`), `/api/history`, `/api/settings` (GET/POST —
POST принимает частичный `SettingsUpdateRequest`, любое поле пишется
немедленно, "кнопки сохранить" в интерфейсе намеренно нет — см. ниже),
`/api/diagnostics` (версия yt-dlp + наличие ffmpeg в PATH), `/api/ytdlp/update`
(`pip install -U yt-dlp` синхронно).

`add_to_queue()` подставляет `settings.ensure_download_folder()` в
`output_folder`, если фронтенд его не прислал (фронтенд никогда не шлёт папку
явно — раньше из-за этого файлы падали в рабочую директорию процесса вместо
папки из настроек).

## Фронтенд (`frontend/src`)

React + TypeScript + Tailwind v4 + framer-motion, без роутера — навигация
между тремя "страницами" (`home`/`history`/`settings`) — просто `useState<Page>`
в `App.tsx`, условный рендер. Общаются с бэкендом через `services/api.ts`
(fetch-обёртка над `/api/*`) и `services/ws.ts` (`useWsEvents` — держит один
`WebSocket`, автопереподключение через 1.5с при обрыве).

- **`hooks/useDownloads.ts`** — вся логика активных загрузок: `jobs`
  (`Record<id, DownloadJob>`), обработчик `WsEvent` (`progress`/`status`/`log`/
  `error`/`finished`), `addToQueue`/`pause`/`resume`/`cancel`/`dismiss`.
  Job попадает в стейт только через `addToQueue()` (свой запрос) — WS-события
  для неизвестного `id` тихо игнорируются (`prev[event.id] ? ... : prev`).
  На каждом (пере)подключении WebSocket вызывается `syncQueue()` — состояние
  очереди дотягивается с бэкенда, так что перезагрузка окна больше не «теряет»
  идущие загрузки.
- Завершённые (`completed`) джобы сами убираются из списка через 8с — или почти
  сразу, если в настройках включено «Убирать из очереди после загрузки»
  (раньше этот переключатель сохранялся, но не влиял ни на что), у карточек в терминальном статусе
  (`completed`/`failed`/`cancelled`) есть ручная кнопка-крестик (`DownloadCard`) —
  раньше не было ни того, ни другого, отсюда жалоба "уведомления не убираются".
- **`context/SettingsContext.tsx`** — глобальный стейт настроек, один `fetch`
  на mount всего приложения, `patch()` шлёт частичный PATCH и применяет
  `data-theme` атрибут на `<html>` немедленно. **Кнопки "Сохранить" в настройках
  нет намеренно** — каждое изменение (тумблер, чекбокс, выбор) применяется
  сразу же через `patch()`; `Settings.tsx` после успешного патча на 1.5с
  показывает зелёную галочку "Сохранено" как подтверждение (раньше такого
  подтверждения не было — казалось, что изменения не сохраняются, хотя на
  деле сохранялись всегда).
- **`i18n/translations.ts`** — не библиотека, самодельный `dict` + `useT()`
  хук, читает `language` из `SettingsContext`. Ключи — плоские строки вида
  `"settings.theme"`. **`useT()` обязан возвращать стабильную (мемоизированную)
  функцию** — это не стилистика, а корректность: `App.tsx` держит `t` рядом с
  эффектом анализа ссылки, и нестабильная ссылка запускала бесконечный цикл
  «анализ → ре-рендер → новый `t` → анализ». См. раздел «Разбор трёх симптомов».
- **`index.css`** — Tailwind v4 `@theme`-токены (цвета) под `@layer theme`;
  светлая палитра — отдельный блок `:root[data-theme="light"] { ... }` в том
  же слое (без этого светлая тема была физически невозможна — CSS для неё
  просто не существовал).

## Упаковка в EXE / трей (эта сессия)

Цель: `NeoLoader.exe` двойным кликом — без отдельного `python main.py`, без
открытия localhost вручную, без второго запущенного процесса при повторном
клике.

- **`build.spec`** — PyInstaller onefile. `datas` включает весь
  `frontend/dist/` и `assets/icon.ico`. `hiddenimports` явно собирает
  `collect_submodules("uvicorn")`/`collect_submodules("websockets")` — обе
  библиотеки выбирают конкретную реализацию (loop/http/ws) через `importlib`
  по строке `"auto"`, статический анализ PyInstaller это не видит и без
  явного списка сборка падает в рантайме `ModuleNotFoundError`.
- **Персистентность при `sys.frozen`**: `core/settings_manager.py` пишет
  настройки в `%APPDATA%\NeoLoader`, а не рядом с exe (onefile распаковывается
  в temp при каждом запуске — там ничего не переживает перезапуск).
- **`ui/web_window.py`**: путь к `frontend/dist/index.html` резолвится через
  `sys._MEIPASS` при `sys.frozen`, а не `__file__`-относительный путь (тот
  ломается под onefile — ресурсы лежат не рядом с исполняемым файлом).
  Закрытие окна крестиком (`closeEvent`) теперь прячет окно (`hide()`), а не
  закрывает процесс — реальный выход только через пункт "Выход" в трее,
  который дёргает `close_for_real()` (снимает флаг-предохранитель) + `QApplication.quit()`.
- **`ui/tray.py`** — `QSystemTrayIcon` с `QMenu`: верхний disabled-пункт —
  живой статус ("Качается: N", обновляется раз в 3с через `QTimer` и заново
  при каждом открытии меню через `aboutToShow`), дальше "Открыть NeoLoader" и
  "Выход". Левый/двойной клик по иконке — тоже открывает окно
  (`QSystemTrayIcon.activated`). Правый клик — системное контекстное меню,
  Qt показывает его сам (никакого дополнительного кода не нужно).
- **`ui/single_instance.py`** — `QLocalServer`/`QLocalSocket` под именем
  `NeoLoaderSingleInstance`. `try_acquire()` пытается подключиться к уже
  существующему серверу; если получилось — шлёт `b"show"` и возвращает
  `False` (текущий процесс должен тут же завершиться, ничего не поднимая);
  если нет — сам поднимает `QLocalServer` под этим именем. **Важно**: вызов
  идёт **после** создания `QApplication` в `main.py` — `QLocalSocket` без
  живого `QCoreApplication` не может даже установить соединение (это был
  реальный баг при первой реализации в этой сессии: проверка стояла до
  `QApplication(sys.argv)`, из-за чего второй запуск не находил первый и
  просто открывал второе окно + второй uvicorn на том же порту — сейчас
  протестировано и подтверждено фиксом: второй `NeoLoader.exe` корректно
  завершается сам, процессов остаётся столько же, сколько было).
- **`assets/icon.ico`** — сгенерирован программно (`Pillow`, круг + стрелка
  вниз, циан→фиолетовый градиент, geometрически повторяет
  `frontend/public/app-icon.svg`) — используется и как иконка EXE
  (`build.spec: icon=`), и как `QApplication.setWindowIcon`/иконка трея в
  рантайме.

### Известное ограничение упаковки

`ffmpeg`/`ffprobe` **не бандлятся** в EXE — приложение по-прежнему полагается
на `shutil.which("ffmpeg")` (системный PATH). На машине разработки они стоят
(`C:\Program Files\ffmpeg\bin`), поэтому вся сборка и тестовые скачивания в
этой сессии прошли с постпроцессингом (merge, remux русской дорожки). На
машине без установленного ffmpeg приложение всё равно запустится и скачает
прогрессивные (muxed) потоки, но merge отдельных video+audio дорожек и
remux языкового тега — молча пропустятся (`_tag_ru_audio` просто возвращается,
если `shutil.which("ffmpeg")` вернул `None`). Если понадобится "совсем без
танцев с бубнами" на чужой машине без ffmpeg — следующий шаг — бандлить
статические `ffmpeg.exe`/`ffprobe.exe` в `datas` (лицензия FFmpeg это
разрешает, бинарники добавляют ~80-100МБ).

## Самая дорогая ловушка сборки: `sys.stdout is None`

Симптом у пользователя: EXE запускается, окно открывается, **всё** мертво —
кнопки настроек ничего не делают, любая попытка скачать даёт «Can't reach the
app's background service». То же самое и в браузере.

Причина — одна строка в чужой библиотеке:

```
File "uvicorn/logging.py", line 42, in __init__
AttributeError: 'NoneType' object has no attribute 'isatty'
ValueError: Unable to configure formatter 'default'
```

PyInstaller с `console=False` запускает процесс вообще без консоли, и Python
выставляет `sys.stdout`/`sys.stderr` в **`None`**. `uvicorn.Config()` в
конструкторе настраивает цветное логирование и спрашивает у stdout `isatty()`.
Исключение убивало поток с API целиком: порт 8756 никто не слушал, окно
открывалось пустым, а интерфейс честно сообщал, что не может достучаться до
бэкенда. Скачивание, настройки, история, саммери — всё зависит от этого порта,
поэтому один упавший поток выглядел как «сломалось вообще всё».

**Почему это пережило проверку и попало к пользователю.** Баг не воспроизводится
ни при запуске из исходников (`python main.py` — stdout настоящий), ни при
запуске EXE с перенаправлением (`NeoLoader.exe > log.txt` — перенаправление само
создаёт валидный поток). Он воспроизводится **только двойным кликом**. Проверка
через `NeoLoader.exe > exe.log 2>&1` давала зелёный результат на полностью
нерабочей сборке.

> Правило проверки для этого проекта: собранный EXE тестируется запуском
> **без единого перенаправления** (`Start-Process NeoLoader.exe`), затем
> проверяется, что порт реально в `LISTENING`, и только потом всё остальное.

Что сделано:

* `core/std_streams.py` — `ensure_std_streams()` вызывается **первой строкой**
  `main.py`, до импорта uvicorn: stdout уходит в devnull, stderr — в
  `stderr.log` рядом с `app.log`, stdin — в devnull. Теперь любая библиотека,
  трогающая потоки, не падает, а вывод из C-уровня не теряется;
* `uvicorn.Config(log_config=None, access_log=False)` — uvicorn вообще не
  трогает logging, своё у нас уже есть;
* `ApiSupervisor` (в `main.py`) — API живёт под присмотром и перезапускается до
  3 раз; ловится `BaseException`, потому что uvicorn при неудачном bind зовёт
  `sys.exit()`, то есть бросает `SystemExit` — мимо `except Exception`;
* порт выбирается из диапазона 8756–8765 и передаётся фронтенду
  query-параметром `?api=<port>` (`ui/web_window.py` → `frontend/src/config/app.ts`),
  так что занятый 8756 больше не смертелен;
* если бэкенд всё-таки не поднялся — показывается нативный QMessageBox с
  причиной и путём к `app.log`, а не безмолвно мёртвое окно;
* `SettingsContext` вместо разовой загрузки держит health-poll и отдаёт
  `online`; `OfflineBanner` и страница настроек говорят «фоновая служба не
  запущена» вместо пустого экрана (`if (!settings) return null` и читалось как
  «не работают кнопки настроек»);
* `_LoggingPage` пробрасывает `console.*` из QWebEngineView в `app.log` — до
  этого ошибки внутри React в windowed-сборке были невидимы полностью.

## Разбор трёх симптомов («не работают настройки / вечная загрузка / нет дубляжа»)

Три жалобы выглядели независимыми, а корней оказалось два.

### 1+2. «Вечная загрузка видео» и «не работают настройки» — один корень

`useT()` возвращал **новую стрелочную функцию на каждый рендер**, а `App.tsx`
держал её в зависимостях `useEffect`, который запускает разбор ссылки. Цикл:

```
analyze завершился -> setInfo() -> ре-рендер -> новая t -> эффект перезапустился
        -> analyze ... (бесконечно)
```

Каждая итерация — новый запрос к `/api/analyze`, а один разбор через yt-dlp
занимает 10–25 секунд. Дальше срабатывал второй, бэкендовый дефект: эндпоинты
были объявлены синхронными (`def`, не `async def`), а такие FastAPI выполняет в
**общем** пуле потоков (по умолчанию 40 воркеров). Поток одинаковых 20-секундных
разборов выедал пул целиком — и `/api/settings`, `/api/queue`, `/api/diagnostics`
вставали в очередь за ним. Отсюда «настройки не открываются»: они и не могли.

Что сделано:

* `useT()` мемоизирован (`useCallback`, зависимость — только язык); эффект
  анализа зависит **только** от `url`, текст ошибки берётся через `tRef`;
  запрос отменяется `AbortController` при смене ссылки;
* быстрые эндпоинты переведены в `async def` (выполняются прямо в event loop);
* `/api/analyze` и `/api/summary` уехали в **отдельные ограниченные**
  `ThreadPoolExecutor` (2 воркера) — они физически не могут занять общий пул;
* у `/api/analyze` появились дедупликация «в полёте» (параллельные запросы на
  один URL ждут один результат) и TTL-кэш на 10 минут.

Замер после правки: 6 одновременных `/api/analyze` одного URL — 7.3с суммарно
на один поход в YouTube; повторный запрос — 0.001с из кэша; `/api/settings`
сразу после тяжёлого разбора — 0.001с. В живом UI на вставку ссылки уходит
ровно **один** POST `/api/analyze` (проверено по списку сетевых запросов).

### 3. «Скачивается будто с дубляжом, а дубляжа нет»

Три отдельные причины, все три чинились:

1. **Сравнение языка строкой `== "ru"`** мимо `ru-RU` (см. `normalize_lang`).
2. **Планы без ru-дорожки могли оказаться первыми** — если под фильтр кодека не
   попадал ни один video-only поток, план «видео + ru» не строился вовсе, и
   первым шёл progressive-поток с оригинальным звуком. Починено лестницей
   качества и инвариантом ru-first (см. `core/resolver.py`).
3. **Проверка результата была фиктивной.** `_verify_download()` сначала
   безусловно проставлял файлу тег `language=rus` через ffmpeg, а потом
   «проверял» язык через ffprobe — то есть проверял ровно то, что сам же
   только что и записал. Сходилось всегда, предупреждение не появлялось
   никогда. Теперь источник правды — `info_dict`, который yt-dlp вернул из
   `extract_info(download=True)` (`downloaded_audio_language()` читает
   `requested_formats[*].language`), тег дописывается **только после**
   подтверждения, а если дорожка не русская — в UI уходит сообщение уровня
   `error`, и в историю пишется `ru_dub: false`.

Плюс случай «ru-дорожки нет ни в одном плане» раньше не логировался вообще
(предупреждение висело только на переходе между планами, `i > 0`) — теперь
это явное сообщение об ошибке.

## Саммери по видео (`core/summarizer.py`)

`POST /api/summary` → субтитры (ручные приоритетнее авто) через yt-dlp →
разбор `json3`/`vtt`/`ttml` с дедупликацией «лесенки» авто-титров → сжатие:

* если в настройках задан `summary_api_key` — через Anthropic SDK
  (модель из `summary_model`, по умолчанию `claude-opus-5`);
* иначе — встроенный экстрактивный алгоритм (частотное взвешивание
  предложений, без сети и без ключа).

Если вызов Claude падает (неверный ключ, лимит, нет сети) — не роняем фичу,
отдаём локальное саммери и `fallback_reason`. Сам ключ наружу не отдаётся:
`GET /api/settings` возвращает `summary_api_key: ""` и флаг
`summary_api_key_set` (см. `SettingsManager.public_settings()`).

## Нативные диалоги из HTTP-потока (`ui/dialogs.py`)

Кнопка «выбрать папку загрузок» вызывает обычный эндпоинт, живущий в потоке
uvicorn, а `QFileDialog` можно создавать только в GUI-потоке. Запрос уезжает в
главный поток через сигнал (`AutoConnection` из другого потока = `QueuedConnection`),
вызывающая сторона ждёт `threading.Event` с таймаутом. `install()` вызывается из
`main.py` после создания `QApplication`. До этого путь к папке загрузок был
нередактируемым текстом — то есть эта часть настроек была декорацией.

## Два бага, которые ломали ТОЛЬКО собранное приложение

Оба воспроизводились исключительно двойным кликом по EXE и были невидимы при
любом другом способе запуска. Из-за этого прошлые проверки их пропускали.

### 1. `sys.stdout is None` убивал поток API

PyInstaller с `console=False` запускает процесс без консоли, и Python выставляет
`sys.stdout`/`sys.stderr` в `None`. `uvicorn.Config()` в конструкторе настраивает
цветной формат логов и зовёт `sys.stdout.isatty()`:

```
File "uvicorn/logging.py", line 42, in __init__
AttributeError: 'NoneType' object has no attribute 'isatty'
ValueError: Unable to configure formatter 'default'
```

Поток с API умирал ещё до bind(). Порт никто не слушал, окно открывалось, и
весь интерфейс отвечал «фоновая служба не запущена».

**Почему это не ловилось:** из исходников (`python main.py`) stdout настоящий.
И — что важнее — при запуске EXE с перенаправлением (`NeoLoader.exe > log.txt`)
перенаправление САМО создаёт валидный поток. То есть любая проверка, которая
собирает вывод в файл, маскирует баг. Проверять нужно `Start-Process` без
перенаправления, то есть ровно так, как запускает пользователь.

Починено: `core/std_streams.py::ensure_std_streams()` вызывается первой строкой
`main.py`, до импорта uvicorn (stdout в devnull, stderr в `stderr.log` рядом с
`app.log`), плюс `uvicorn.Config(log_config=None, access_log=False)` — чтобы
uvicorn вообще не трогал логирование.

### 2. `file://` не может делать fetch на `http://`

Окно грузило `frontend/dist/index.html` как `file://`. В QtWebEngine атрибут
`LocalContentCanAccessRemoteUrls` по умолчанию ВЫКЛЮЧЕН, поэтому страница с
локального файла не может обратиться к `http://127.0.0.1:8756`. Каждый `fetch`
падал ещё до сети — при полностью живом и слушающем бэкенде.

Симптом ровно такой, каким его описал пользователь: «через браузер скачивается,
а приложение пишет, что фоновая служба не запущена». Браузер открывает страницу
по `http://` и ограничения не имеет; окно приложения — имеет.

Починено архитектурно, а не флагом: **статика фронтенда смонтирована в сам
uvicorn** (`api/server.py`, `StaticFiles` на `/`, монтируется последней, чтобы не
перехватывать `/api/*` и `/ws`), а окно открывает `http://127.0.0.1:<порт>/`.
Тогда страница и API — один origin: нет `file://`, нет CORS, не нужно передавать
порт во фронтенд (`config/app.ts` берёт `location.origin` в продакшен-сборке).
Атрибуты `LocalContentCanAccessRemoteUrls`/`LocalContentCanAccessFileUrls` всё
равно включены в `ui/web_window.py` — как страховка на случай отката к `file://`.

### Что добавлено, чтобы это не повторилось

* **`ApiSupervisor`** (`main.py`) — держит uvicorn живым и перезапускает до 3 раз;
  падение при старте больше не означает «мёртвое приложение до перезапуска».
* **Выбор порта** — если 8756 занят, берётся следующий свободный из 8756-8765.
* **Диалог об ошибке** — если бэкенд так и не поднялся, пользователь видит
  `QMessageBox` с причиной и путём к `app.log`, а не молча мёртвое окно.
* **Баннер «фоновая служба не запущена»** в интерфейсе + постоянный health-poll
  (`SettingsContext`): состояние названо вслух, и UI сам оживает, когда бэкенд
  поднимается. Страница настроек больше не рендерит пустоту (`return null`).
* **console.* со страницы пишется в `app.log`** (`ui/web_window.py::_LoggingPage`),
  а фронтенд специально печатает `[neoloader] backend online|unreachable at <base>`.
  В собранном приложении devtools нет — это единственный способ увидеть постфактум,
  дошёл ли интерфейс до бэкенда. Именно эта строка и подтвердила починку.
* **Файловый handler повешен на общий логгер `neoloader`**, а не на два конкретных —
  до этого всё из `neoloader.window`/`.api`/`.summary` пропадало бесследно.

## Конвертер: почему отдельный модуль и отдельная очередь

Вкладка «Конвертер» — это ffmpeg над УЖЕ СКАЧАННЫМИ файлами, без сети и без yt-dlp.
Идея и набор операций взяты у Shutter Encoder, включая главную его особенность:
если операцию можно выполнить без перекодирования, она выполняется без него.

### Что именно делается без потерь

`core/media_tools.py` держит матрицу «контейнер -> какие кодеки он умеет хранить»
(`CONTAINERS`). Перед сменой контейнера каждый поток исходника сверяется с этой
матрицей, и в команду ffmpeg попадает `-c:v:0 copy` / `-c:a:1 copy` для всего, что
влезает как есть. Перекодируется РОВНО тот поток, который мешает: h264 -> .webm
перекодирует видео в vp9, но дорожка субтитров и всё остальное копируются.

Обрезка: `-ss` ДО `-i` плюс `-c copy` — мгновенно, ценой сдвига начала к ближайшему
ключевому кадру (декодировать с середины GOP без перекодирования физически нельзя).
Точный режим ставит `-ss` ПОСЛЕ `-i` и перекодирует. Пользователю это сказано словами
в интерфейсе, а не спрятано.

Замена дорожки: `-map 0:v:0 -map 1:a:0 -c:v copy` — видеопоток не читается и не
пишется заново вообще, меняется только звук.

Каждая задача возвращает флаг `lossless`, и он виден в списке операций. Это ответ
на единственный вопрос, который реально волнует: потерялось ли качество.

### Почему очередь отдельная от загрузок

У них разные узкие места. Загрузка упирается в сеть, и пять параллельных потоков её
ускоряют — поэтому `concurrent_downloads` доходит до 5. ffmpeg упирается в процессор,
и пять одновременных перекодирований делают каждое из них в пять раз медленнее,
заодно подвешивая интерфейс. `MediaJobManager` держит `MAX_PARALLEL_JOBS = 2`: второй
слот нужен только чтобы быстрый ремукс не ждал часовое перекодирование.

`MediaJobManager` намеренно НЕ QObject и не использует Qt-сигналы, в отличие от
`DownloadManager`: ему нужен ровно один callback наружу (`on_event`), который
`api/server.py` подключает к тому же WebSocket. Меньше машинерии — меньше мест, где
сигнал может потеряться между потоками.

Менеджер создаётся в `main.py` и живёт ДОЛЬШЕ, чем приложение FastAPI: `ApiSupervisor`
при падении uvicorn создаёт новый `app`, и если бы очередь конвертаций принадлежала
ему, она обнулялась бы прямо посреди часового перекодирования.

### Прогресс и отмена

Прогресс читается из `-progress pipe:1` (поле `out_time_us`) и делится на длительность
из ffprobe — одинаково для всех операций, в отличие от парсинга stderr. stderr при этом
вычитывается отдельным потоком: у ffmpeg он может заполнить буфер трубы и намертво
заблокировать процесс, если читать только stdout.

Отмена и любая ошибка УДАЛЯЮТ недописанный выходной файл. Иначе на диске остаётся
обрезок, который по имени и размеру выглядит как готовый результат.

### Список кодеков — из системы, а не из кода

`available_encoders()` один раз за процесс парсит `ffmpeg -encoders` и кэширует
результат; `/api/media/capabilities` отдаёт фронтенду только те кодеки, для которых
энкодер реально нашёлся. Минимальные сборки ffmpeg идут без libx265/libsvtav1, и
захардкоженный в TypeScript список обещал бы пользователю кодек, которого у него нет.

## Плейлисты и каналы: почему N задач, а не одна

`fetch_playlist_entries` (`core/video_info.py`) разбирает список через
`extract_flat="in_playlist"` — один запрос на страницу списка, без похода в каждое
видео: тысяча роликов разбирается за секунды вместо часов. Верхняя граница
`MAX_PLAYLIST_ENTRIES = 500` стоит и в разборе, и в анализе — иначе канал на 3000
роликов постранично тянется ВЕСЬ только ради счётчика в превью.

Ссылка на канал (`/@handle`, `/channel/UC...`, `/c/...`, `/user/...`) раньше не
распознавалась вообще: в ней нет ни `v=`, ни `list=`, и `detect_link_type` возвращал
INVALID. Добавлен тип `CHANNEL`, а `channel_videos_url()` дописывает `/videos` —
голая ссылка на канал отдаёт не список роликов, а список ВКЛАДОК, и разбор возвращал
бы четыре псевдо-«видео» с названиями вкладок.

`POST /api/queue/batch` ставит каждое выбранное видео ОТДЕЛЬНОЙ задачей. Одна задача
«скачай плейлист» означала бы, что нельзя ни выбрать три ролика из сорока, ни отменить
один из них, а падение любого видео (приватного, удалённого, заблокированного по
региону) роняло бы всю загрузку целиком.

`ignoreerrors=True` нужен, чтобы одно приватное видео внутри списка не роняло разбор
остальных. Побочный эффект: при недоступном САМОМ списке yt-dlp не бросает исключение,
а возвращает None — этот случай проверяется явно, иначе наружу уходило
`'NoneType' object has no attribute 'get'` вместо понятного сообщения.

## Очередь загрузок: пауза ожидающих и порядок

Пауза раньше работала только для АКТИВНОЙ задачи, поэтому «придержать очередь» было
невозможно: остановишь текущую — тут же стартует следующая. Теперь `pause_item`
переводит ожидающую задачу в PAUSED, а `_launch_available` берёт только PENDING,
так что она просто не запускается.

Пауза, нажатая во время анализа, вступает в силу только в progress-хуке (единственная
безопасная точка прерывания — `QThread.terminate()` может повредить файл). До этого
статус успевал перезаписаться на `analyzing`/`downloading`, и интерфейс показывал
«качается» у намертво замершей задачи. Статус теперь приводится в соответствие прямо
в хуке, там же, где пауза реально срабатывает.

Сортировка карточек во фронтенде шла по `job.id` (uuid) — то есть порядок был
случайным и не совпадал ни с очередью бэкенда, ни с порядком добавления. С кнопками
«вверх/вниз» это стало прямой ложью. Теперь активные и ожидающие сортируются по
`position` из бэкенда, завершённые уходят вниз в порядке появления.

Событие о задаче, которой нет в локальном списке, раньше просто игнорировалось —
и очередь показывала «нет активных загрузок» при живой загрузке (задачу добавили из
другого окна, или бэкенд перезапустился при открытом сокете). Теперь такое событие
запускает дебаунсированный ресинк `/api/queue`.

## Один WebSocket на приложение

`useWsEvents` открывал СОБСТВЕННОЕ соединение на каждый вызов. Пока подписчик был один
(очередь загрузок), это было незаметно; со второй подпиской (задачи конвертера)
приложение стало бы держать два сокета к своему же бэкенду, а сервер отправлял бы
каждый broadcast дважды. Соединение переехало в модуль: один сокет, набор подписчиков,
переподключение и закрытие по последнему отписавшемуся.

## Проверено в этой сессии

- Полный build → запуск → повторный запуск (single-instance) → добавление
  реальной загрузки через `/api/queue` → live-мониторинг `/ws` (raw Python
  `websockets`-клиент) → троттлинг подтверждён (~1.4 progress-события/сек
  вместо потенциальных сотен) → параллельные вызовы `/api/settings`,
  `/api/diagnostics` во время активной загрузки (50-90мс, без деградации) →
  фронтенд через Vite dev-сервер на том же живом бэкенде: страница "Настройки"
  открывается мгновенно во время активной загрузки, live-тема продолжает
  работать.
- Тестовая загрузка: `https://www.youtube.com/watch?v=ud7wzdiM0gk` с
  `neuro_dub_ru=true` — RU-дорожка подтверждена в сырых форматах yt-dlp
  (`format_id 251-5`, `format_note "Russian, medium"`) до старта скачивания.

Дополнительно (сессия с разбором трёх симптомов):

- Сквозная загрузка через `DownloadManager` с `neuro_dub_ru=true` и заведомо
  «неудобным» `video_codec="av1"`: инвариант ru-first выполнен, лог
  `DUB_CONFIRMED lang=ru`, `ru_dub_confirmed=True`, `ffprobe` на итоговом
  MP4 показывает `rus`. Раньше именно эта комбинация давала progressive-поток
  с оригинальным звуком.
- Проверено побайтово, что языковые `format_id` действительно разные дорожки:
  `140-14` (`language=ru`) и `140-23` (`language=en-US`) дают файлы с разными
  MD5 при одинаковом размере.
- 6 параллельных `/api/analyze` одного URL → один поход в YouTube (7.3с),
  повтор из кэша 0.001с, `/api/settings` под нагрузкой 0.001с.
- `POST /api/settings` с ключом API: ключ сохранён на диск, наружу отдаётся
  пустая строка + `summary_api_key_set: true`.
- `POST /api/summary` на реальном видео: 200, `engine=local`, транскрипт
  21893 символа, 7 тезисов.
- Живой UI (Vite dev-сервер поверх работающего бэкенда): вставка ссылки —
  ровно один `POST /api/analyze`; страница настроек рендерится целиком;
  смена «качества по умолчанию» долетает до диска и подставляется в форму
  новой загрузки (раньше `DEFAULT_FORMAT` был захардкожен и настройка не
  влияла ни на что).
- Межпоточный путь выбора папки проверен отдельно (подменённый
  `QFileDialog.getExistingDirectory`): слот выполняется в `MainThread`,
  результат возвращается в вызывающий поток.

Сессия с починкой собранного приложения (запуск через `Start-Process` без
перенаправления потоков — эквивалент двойного клика):

- `app.log` собранного EXE: `API готов, порт 8756`, затем `Открываю собранный
  фронтенд с http://127.0.0.1:8756`, затем `[web] [neoloader] backend online at
  http://127.0.0.1:8756`. Последняя строка приходит из React ВНУТРИ окна
  приложения, а не из браузера — то есть интерфейс окна реально достучался до API.
- uvicorn отдаёт `/` (index.html), `/assets/*.js`, `/assets/*.css`, `/favicon.svg`
  с корректными content-type, и `/api/*` на том же origin.
- **Сквозная загрузка с русским дубляжом через интерфейс приложения**: MrBeast
  `0e3GPea1Tyg`, 360p/h264, галка «Russian audio track». Результат — файл 97.7 МБ
  в папке загрузок, `ru_dub: true` в истории, ffprobe: `stream_tags=language=rus`.
- **Доказательство, что дорожка настоящая, а не просто тег**: декодированный в
  PCM (16 кГц моно, окно 300-320 с, `-ss` ПОСЛЕ `-i` — посемпльно точный отсчёт)
  звук файла даёт MD5 `ece183d1...`, что БАЙТ В БАЙТ совпадает с эталонной
  русской дорожкой `140-14` и отличается от английской `140-23` (`136032f8...`).
  То же самое подтверждено для режима «только аудио».
  Первая попытка сравнения с `-ss` ДО `-i` дала расхождение — это артефакт
  выравнивания по пакетам при seek, а не разница содержимого; отсчёт на выходе
  снимает вопрос.
- Отзывчивость под нагрузкой: 276 запросов к `/api/settings`, `/api/queue`,
  `/api/diagnostics`, `/api/history` во время активной загрузки — медиана
  10.8 мс, максимум 158 мс.

Сессия с конвертером и пакетной загрузкой:

- Все 10 операций конвертера прогнаны через живой HTTP-API (`/api/media/jobs`) и
  завершились успешно: ремукс в MKV, обрезка без перекодирования и точная, извлечение
  аудио «как есть» и в FLAC, замена дорожки, конвертация copy->MKV, конвертация с
  перекодированием в H.264 240p, GIF, кадр в JPEG.
- Флаг `lossless` совпал с реальностью: ремукс, обрезка `-c copy`, замена дорожки и
  конвертация copy->MKV помечены как без потерь; перекодирования — нет.
- ffprobe по результатам: `_cut.mp4` = h264+aac(rus), `_cut.mkv` = h264+aac(rus),
  `_cut.webm` = vp9+opus(rus) (h264/aac в WebM не помещаются — перекодированы ровно
  эти два потока), `_cut_newaudio.mp4` = h264+mp3(rus) при нетронутом видеопотоке.
- Ремукс 30-секундного фрагмента: 0.1 с. Перекодирование того же фрагмента в WebM:
  61.6 с. Разница — ровно то, ради чего сделан режим без перекодирования.
- Режим «только аудио: original» проверен сквозной загрузкой: результат — opus в .webm
  (134 kbps, нативный поток YouTube, постпроцессор не запускался). Тот же ролик в
  режиме mp3/320 — mp3 320 kbps. Раньше значение "original" уходило в
  `preferredcodec` как есть, и постпроцессор yt-dlp падал на списке поддерживаемых.
- Разбор канала `@MrBeast`: `link_type=channel`, 500 записей (упёрлось в лимит).
  Разбор плейлиста из 5 роликов — 1.4 с, повторный запрос из кэша — 0.001 с.
- Пакетная постановка 4 роликов одним запросом, `pause_all` затронул все 4,
  перестановка последней задачи на первую позицию отработала, `clear` убрал 3
  ожидающих и не тронул активную.
- В живом интерфейсе (собранный фронтенд, `http://127.0.0.1:8756/`): вкладка
  «Конвертер» открывается, плейлист рисуется таблицей с длительностями и фильтром,
  панель очереди показывает «Пауза для всех»/«Продолжить все»/«Убрать ожидающие (3)»,
  кнопка «вниз» реально переставляет задачу, а задача, добавленная в обход интерфейса,
  появляется в списке без перезагрузки страницы.

Сессия с `sys.stdout is None` — проверка велась на собранном EXE, запущенном
`Start-Process` без перенаправления, то есть ровно как двойным кликом:

- порт 8756 в состоянии `LISTENING`; `app.log` без единого ERROR/WARNING,

- у процесса NeoLoader есть установленное соединение с 8756 — значит React
